# 账号封禁风险（实测记录）

> 2026-11-10 更新。**使用本代理会导致你的 DeepSeek 网页版账号被风控封禁。**

## 实测结果

- 2026-11-09 对 `chat.deepseek.com` 网页端接口进行自动化调用后，账号被
  **直接封禁 9 天**（临时封禁，不是永久停用）。
- **后续处罚可能更长**：再次触发时封禁时长可能升级，不排除永久停用账号。
- 项目已内置 `upstream_pacing`（`DEEPSEEK_MAX_CONCURRENCY=2`、
  `DEEPSEEK_MIN_INTERVAL_MS=800`、`DEEPSEEK_MAX_RETRIES=2`），并做了
  `INVALID_TOKEN` 令牌自愈；**这些缓解措施没能避免本次封禁**。
  不要以为「加了限流就安全」。

封的是**网页版账号本身**，不是某个 API Key；换 token 不等于换账号。

## 为什么会触发

本代理不是官方 API：它复用浏览器的 `userToken`、`did` 设备标识和 PoW 挑战，
直接请求网页端私有接口。上游风控可以依据（不限于）：

- 非浏览器指纹的请求头 / TLS 行为
- 请求频率、并发度与时序规律性（自动化特征）
- 每次请求重复的 PoW 计算，以及 `/chat/continue`、`/chat/resume_stream`
  状态机重放
- 单账号长时间在线、多会话并发
- 把 system prompt 与 `tools` 定义拼进单条超长消息的
  **function calling 桥接**场景——这类请求体更大、更规律，同样走网页端接口

⚠️ **任何基于同一套网页登录态的封装都共享这个风险**：把本代理挂进 DSH、
第三方客户端、或任何「备用 provider / 备用模型」配置里长期在线调用，
触发的是同一个账号的同一套风控。多个客户端共用一个账号只会更快出事。

## 使用建议（只能降低概率，不能保证免封）

1. **绝不要用主力账号**，也不要用绑定了重要数据、付费或历史会话的账号。
   用专门的、丢得起的小号。
2. 保持低频、低并发；不要跑批量探测、循环健康检查、压测或自动化脚本连打。
3. 不要 7×24 挂在 Agent / 客户端里当默认模型；需要时才启动，用完停掉代理进程。
4. 关注 `GET /deepseek/health` 的 `token_status`。一旦出现 `INVALID_TOKEN`、
   异常验证要求或频繁 401/403，**立即停止**，不要靠「自动重扫浏览器
   Local Storage 换 token」硬扛——那只会把新会话继续送进风控。
5. 不要在同一账号上同时运行多个代理实例或多个客户端。
6. 需要稳定、合规的调用请使用官方 API，并遵守 DeepSeek 服务条款。

## 已经被封了怎么办

- **立即停止所有请求**，关闭代理与看门狗进程，不要再发任何一条消息试探。
- 等待封禁期结束（本次为 9 天）。期间反复重试、换 token 或换设备标识，
  可能让处罚升级、时长变长。
- 解封后若继续使用本代理，风险不变，且下次处罚可能更重。
- 本仓库作者与维护者不对账号封禁、数据丢失或任何连带后果负责。
